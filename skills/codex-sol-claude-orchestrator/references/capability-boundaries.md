# Capability boundaries

Read only for critical bottlenecks, ineffective repairs, difficult algorithms/modeling, or visuals. These are routing cues, not a benchmark or guaranteed ceiling. Model aliases, provider bridges, and available tools must be verified separately. Do not change settings while routing.

## Critical work and ineffective repairs

Codex may derive and implement the smallest decisive bottleneck directly when concrete evidence indicates CC is a poor fit; no failed CC attempt is required. Useful signals are long-chain reasoning without a cheap oracle, tightly coupled state/concurrency/lifecycle invariants, contradictory cross-module evidence, or fine visual ambiguity that determines implementation. Ordinary unfamiliar code, difficulty, or an unknown root cause alone still fits bounded CC investigation.

Keep CC-1 for a focused repair while evidence advances. Codex takes over the minimum root-cause/core fix when the same counterexample survives without causal progress, changes mask symptoms or create regressions, or a material decision/unsound approach emerges. Reuse CC's reproduction, hypotheses, attempts, and evidence paths; do not restart broad exploration or send a longer prompt. Delegate stable remainder.

Codex-authored substantive fixes still get fresh CC-2 review where available. Codex runs a key check only when takeover risk or unresolved evidence requires it, not as routine test ownership. Disclose unestablished cause/correctness. Network latency, auth, tool denial, missing artifacts, and incomplete SDK finalization are transport/tool failures, not reasoning evidence.

## Algorithms and modeling

CC defaults include established algorithms, agreed-equation implementation, data preparation, fitting/evaluation against an agreed metric, tests, numerical experiments, and bounded diagnosis. For uncertain work, delegate a falsifiable result: counterexample, instability reproduction, fixed-data comparison, baseline, or prototype.

Codex owns the objective, units/constraints, assumption validity, consequential tradeoffs, and unproved correctness claims; CC may propose/test alternatives and implements the settled design. Use an oracle when needed—small brute force, trusted reference, dimensional/invariant checks, held-out data, or measured error. Agreement between two CC sessions is not an oracle.

## Visuals

Model visual capability does not prove this MCP can pass an attachment: its task API is text, while CC can read accessible local files.

- Delegate raw visual work only when CC can access the local artifact through a verified path; otherwise Codex supplies the accessible asset or a short necessary visual specification.
- Codex resolves ambiguous/fine spatial interpretation, aesthetic choices, and final high-consequence visual judgment; CC can implement or process assets under those constraints.
- Do not repeatedly probe capability or invent inaccessible image content. Codex browser/computer tools and permissions are not inherited.
